B1-1 이해용 강의

외우지 말고 이해하기. 각 장의 파란 박스만 자기 말로 말할 수 있으면 된다.

조작: 방향키 · 스페이스 · 하단 버튼. 주소에 장 번호가 남는다.

0. 전체 지도와 파일 구조

  • 화면 만들기: 반응형 · Flex/Grid · 모바일 퍼스트
  • 움직임 만들기: 이벤트 · STATE · 상태→렌더
  • 바깥 데이터: fetch · 목록 변환 · 폼 검증
  • 안 보이는 배려: 접근성 · FOUC · 디버그
이 강의는 화면 → 움직임 → 데이터 → 배려 순서로 간다. 코드 위치도 이 순서다.

1. 반응형과 미디어쿼리

  • 미디어쿼리는 화면 너비 조건에 따라 다른 스타일을 덧입히는 분기
  • 모바일 퍼스트 = 좁은 화면을 기본으로 쓰고 넓어질 때 덮어쓴다
좁은 화면이 기본, 넓어지면 덮어쓴다. 그래서 저사양·터치 환경이 먼저 보장된다.
왜 데스크톱을 기본으로 안 하는가?

2. Flex vs Grid

  • Flex는 한 축(가로 또는 세로) 정렬용 1차원. 내비 로고 좌측·메뉴 우측이 정석
  • Grid는 행·열 동시 제어용 2차원. 카드 격자가 정석
  • auto-fit minmax(260px, 1fr): 빈칸을 접어 카드를 늘린다
  • 반대 auto-fill은 빈칸을 유지해서 카드가 한쪽으로 쏠린다
한 줄 정렬은 Flex, 격자는 Grid. 카드가 적어도 꽉 차 보이는 건 auto-fit 덕분이다.
내비를 Grid로, 카드를 Flex로 하면 뭐가 불편한가?

3. 테마·저장소·FOUC

<head> 선주입 → 화면 그리기 → 토글 → localStorage 저장 → 새로고침 복원
  • localStorage는 브라우저에 문자열을 저장하는 창고. 새로고침해도 남는다
  • 저장은 try/catch: 막히면 메모리 상태로만 동작한다
  • FOUC = 스타일 전 흰 화면 번쩍임. DOMContentLoaded에서 복원하면 생긴다
  • 그래서 <head> 동기 스크립트로 data-theme을 그리기 전에 박는다
깜빡임의 원인은 복원 시점이다. 그리기 전에 박으면 0이 된다.
선주입 스크립트를 body 끝으로 옮기면 무슨 일이 생기는가?

4. 이벤트와 var 금지

  • defer = 해석을 막지 않고 받아서 해석 끝난 뒤 순서대로 실행. DOM 준비 보장
  • async는 완료 즉시 실행이라 DOM 미완성 위험. 원문은 defer 요구
  • var 금지 이유: 함수 스코프·호이스팅 undefined·중복 선언 허용
  • 기본 const, 재할당만 let. 인라인 onclick 대신 addEventListener
defer는 순서 보장, var 금지는 예측 가능성. 둘 다 나중에 헤매지 않기 위한 규칙이다.
var의 세 가지 문제점을 말해보기.

5. STATE와 상태→렌더

  • STATE = 화면을 결정하는 값을 한 객체에 모은 것. 단일 진실 원천
  • 값은 setState로만 바꾼다. 흩어진 변수보다 추적이 쉽다
이벤트는 값만 바꾸고 그리기는 따로. 흐름이 다섯 개여도 모양은 하나다.
변수 다섯 개로 나눠 관리하면 뭐가 어긋나는가?

6. 스크롤 등장과 임계값

  • scroll 리스너로 직접 계산하면 Reflow·Repaint 반복으로 버벅인다
  • IntersectionObserver = 화면 진입을 브라우저가 비동기로 알려주는 API
  • 임계값 0.2 = 20% 보이면 콜백 실행. 0은 닿자마자, 1은 전부 보여야
  • 한 번 보이면 unobserve로 감시 종료. 맨 위로는 300px, 내비 변경은 60px
스크롤 계산은 브라우저에 맡기고, 기준은 0.2. 다 본 건 감시를 끈다.
임계값을 1로 바꾸면 카드 등장이 어떻게 달라지는가?

7. fetch와 4상태

  • fetch는 404·403에도 실패하지 않는다. 망 단절 때만 catch로 간다
  • 요청은 8초 타임아웃(AbortController), 캐싱 없음
fetch의 함정은 성공처럼 보이는 실패다. ok 검사로 잡는다.
ok 검사를 빼먹으면 403 때 화면이 어떻게 되는가?

8. 목록 변환 3단계

filter로 선별 → map으로 카드 변환 → forEach로 삽입
  • filter: 언어 조건에 맞는 저장소만 고른다
  • map: 객체 1개를 카드 HTML 1개로 바꾼다. 구조분해로 값을 꺼낸다
  • 외부 데이터는 escapeHTML 후 삽입. 스크립트 섞임(XSS) 방지
고르고 → 바꾸고 → 꽂는다. 꽂기 전에 이스케이프가 끼어 있다.
이스케이프 없이 name을 그대로 넣으면 무슨 위험이 있는가?

9. 폼 검증과 접근성 연결

  • submit에서 preventDefault: 안 막으면 검사 결과가 새로고침에 날아간다
  • 빈값·이메일 정규식 검사 후 오류 표시, 입력(input)하면 지운다
  • aria-describedby = 입력칸과 오류 문구를 연결. 스크린리더가 같이 읽는다
  • aria-invalid 토글, 오류 단락은 role=alert로 즉시 알림
검증은 막고·검사하고·알리고. 알리는 쪽은 장애 여부와 무관하게 모두에게 보인다.
preventDefault를 빼면 왜 검증이 소용없어지는가?

10. 스킵링크와 라이브 영역

  • 스킵링크: 키보드 사용자가 내비를 Tab으로 다 넘기지 않고 본문으로 점프
  • 평소엔 화면 밖(top: -100px), Tab 포커스가 오면 나타난다
  • role=status = 상태 변화(목록·전송 결과)를 자동으로 읽어준다
  • aria-expanded = 메뉴 열림 상태를 스크린리더에 전달. JS가 동기화한다
안 보이는 배려 셋트: 건너뛰기 · 자동 읽기 · 상태 전달.
스킵링크 없이 키보드만으로 본문에 가려면 몇 번 눌러야 하는가?

11. 디버그와 기준값

  • __B11_DEBUG: 상태 변경 로그 스위치. 평소엔 꺼져 있어 조용하다
  • 콘솔에 window.__B11_DEBUG = true → 이후 변경이 찍힌다
  • 기준값 3종: 스크롤탑 300px · 내비 60px · 임계값 0.2. 바꾸면 README에 명시
평소엔 조용히, 볼 때만 켠다. 숫자를 바꾸면 문서도 같이 바꾼다.
상시 로그를 켜두면 뭐가 문제인가?
