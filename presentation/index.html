B1-1 이해용 강의

외우지 말고 이해하기. 이번엔 순서를 바꿨다. 개념별로 나열하는 대신, 이 페이지가 답해야 할 열다섯 가지 질문에 따라간다.

매 장은 같은 모양이다. 질문이 뭔지, 이 코드가 실제로 뭘 하는지, 어느 파일 몇 줄에 있는지, 화면에서 뭘 눌러보면 되는지. 파란 박스만 자기 말로 말할 수 있으면 된다.

조작: 방향키 · 스페이스 · 하단 버튼, 모바일에선 좌우 스와이프. 스페이스는 다음 장으로 가니 한 장이 길 때는 휠로 내리세요. 주소에 장 번호가 남는다.

전체 흐름: 모든 장은 이 흐름의 한 지점

  • 사용자 행동을 addEventListener로 받고, 값을 setState로 바꾸고, 적용 함수가 화면을 다시 그린다.
  • 이 순서를 손으로 그리며 말할 수 있으면 뒤의 장 절반은 이미 알고 있는 거다.

리스너 열 곳: js/main.js:36, 54, 64, 71, 143, 157, 164, 171, 234, 272 · setState: js/main.js:19 · STATE: js/main.js:10-15

빈 종이에 이 흐름도를 그리고, 각 칸에 실제 함수 이름을 붙여보자. applyTheme · applyMenu · renderRepos.

문서와 코드가 달랐던 여섯 곳 — 세 곳은 9/19에 코드로 채움

README와 요구사항에 쓰인 말을 그대로 믿고 외우면, 코드를 같이 열어본 순간 말꼬리가 잡힌다. 이 강의는 정정하지 않고 코드의 실제를 그대로 말한다. 2026-09-19에 세 곳(Q1 1200 분기·Q9 위임·Q13 내비 space-between)은 채점표대로 코드를 리팩터링했고, 나머지는 코드의 실제가 답이다.

말코드의 실제
반응형 확인 기준이 360·768·1200px넓히는 분기는 768·1024·1200 세 개다 — 1200 분기는 9/19에 신설했다. 360은 쿼리가 아니라 모바일 퍼스트 기본값이고, 1024는 README에 적히지 않았다. (Q1)
폼 오류에 즉각 피드백처음부터 즉각이 아니었다. 네이티브 검증이 커스텀 문구를 막는 결함을 뒤늦게 발견해서 novalidate와 입력 중 재검사를 추가했다. 그 내력이 Git 로그에 있다. (Q5)
addEventListener의 위임 이점원래는 쓰지 않았지만 9/19에 리팩터링했다. 필터는 이제 부모 리스너 하나 + closest 위임이고, 개선 전후가 Git 로그에 있다. (Q9)
내비는 Flex space-between9/19에 실현됐다. 768px부터 내비가 flex: 1 + space-between이고, 푸터의 space-between은 그대로다. (Q13)
상태 하나가 화면을 결정STATE를 거치는 건 테마·메뉴·목록 세 흐름뿐이다. 폼은 지역 변수, 스크롤은 클래스 토글 바로 간다. (Q14)
저장소 카드 4열1200px 이상에서는 4열로 명시 고정한다(9/19 신설). 그 아래는 auto-fit이 세는 실측: 375px→1열, 800px→2열, 1100px→3열, 1280px→4열. (Q1)
모범 답안을 외우는 게 아니라, 내 코드가 실제로 뭘 하는지 정확히 아는 게 이 강의의 목적이다.
이 표의 여섯 줄 중 세 줄(1200 분기·위임·내비 space-between)은 9/19 커밋 전후 코드가 달라진 자리다. 어느 장에서 무슨 코드가 바뀌었는지로 찾아보자.

Q1. 창을 줄이면 모바일 레이아웃으로 바뀌는가

  • 이 페이지의 미디어쿼리는 세 개다. min-width: 768px에서 내비를 펼치고(space-between 포함) 카드를 2열로, 1024px에서 본문 최대폭을 걸고 기술을 4열로, 9/19에 신설한 1200px에서 본문 열을 1200으로 넓히고 저장소 카드를 4열로 고정한다.
  • 좁은 화면이 기본이다. 360px 분기는 없다. 모바일 퍼스트에서는 기본 스타일 자체가 좁은 화면용이고, 넓어질 때 덧입힌다. 데스크톱을 기본으로 두지 않는 이유는 저사양·터치 환경이 먼저 보장되기 때문이다.

css/style.css:494 768 분기 · :540 1024 분기 · :561 1200 분기 · :509-517 내비 전개(space-between :513-514)

좁은 화면이 기본, 넓어지면 덮어쓴다. 360은 쿼리가 아니라 기본값이다.
DevTools로 767→768에서 햄버거가 가로 메뉴로 바뀌는 것을, 1199→1200에서 카드가 3열에서 4열로 바뀌는 것을 보자.

Q2. 테마 토글이 새로고침 후에도 유지되는가

  • 버튼을 누르면 theme 값이 반전하고, applyTheme이 <html>의 data-theme 속성을 바꾸면서 localStorage에 저장한다. 저장은 try/catch다. 막혀도 화면은 동작한다.
  • 새로고침 후 복원의 주체는 main.js가 아니라 <head>의 인라인 스크립트다. 첫 그림이 그려지기 전에 저장된 값을 읽어 속성을 먼저 박는다. 그래서 흰 화면이 번쩍이는 FOUC가 없다. main.js는 defer라 이보다 늦게 실행된다.
  • 저장된 값이 없으면 OS 설정(prefers-color-scheme)을 따른다.

js/main.js:36-38 토글 · :25-28 applyTheme와 저장 · index.html:13-21 head 선주입

깜빡임의 원인은 복원 시점이다. 그리기 전에 박으면 0이 된다.
다크로 바꾸고 F5. 번쩍임이 없는지. 그리고 head 스크립트를 body 끝으로 옮기면 뭐가 보일지 미리 예상해 보자.

Q3. 메뉴·등장 애니메이션·맨 위로 버튼

  • 햄버거는 setState({menuOpen}) → applyMenu. 메뉴 표시와 aria-expanded를 같은 함수에서 같이 바꿔서, 스크린리더에도 열림 상태가 맞물린다.
  • 등장은 IntersectionObserver다. scroll 리스너로 매번 계산하면 Reflow·Repaint가 반복돼 버벅인다. 브라우저에 감시를 맡기고, 구역이 20%(threshold: 0.2) 보이면 클래스를 붙인 뒤 unobserve로 감시를 끈다. 한 번만 등장한다.
  • 스크롤 이벤트 하나에서 300px를 넘으면 맨 위로 버튼을, 60px를 넘으면 내비 배경을 바꾼다. 클릭하면 scrollTo({behavior:'smooth'}).

js/main.js:54 메뉴 · :47 applyMenu · :64-68 300/60px · :71-72 scrollTo · :77-85 옵저버

계산은 브라우저에 맡기고 기준은 0.2, 다 본 구역은 감시를 끈다. 임계값을 1로 올리면 전부 보여야 등장한다.
메뉴 열고 → 스크롤해서 카드 등장 → 버튼 뜨면 클릭으로 위로. 한 흐름으로 이어서.

Q4. 저장소 목록과 로딩·에러·빈 상태

  • fetch의 함정: 404나 403에도 프로미스는 성공으로 끝난다. 거절되는 건 망이 끊길 때뿐이다. 그래서 res.ok를 직접 검사해서 실패를 내가 만든다.
  • 화면 상태는 넷이다. 로딩 문구 → 성공(문구를 비우고 카드 렌더) / 목록이 비면 빈 결과 문구 / 오류는 403 한도, 404 사용자 없음, 그 외 HTTP, 망 단절·타임아웃으로 나뉜다. 타임아웃은 AbortController로 8초, 재시도는 버튼으로 수동, 캐싱은 없다.

js/main.js:245 로딩 · :200 빈 결과 · :203 성공 · :247-251 8초 · :256-258 상태 분기 · :262-265 catch · :272 재시도

성공처럼 보이는 실패를 ok 검사로 걸러서 넷으로 나눈다. 403은 GitHub 한도(시간당 60회) 초과라는 뜻이기도 하다.
Network 탭을 Offline으로 바꾸고 새로고침해서 오류 상태와 '다시 시도'를, 없는 언어 필터로 빈 결과를 보자.

Q5. 폼 오류에 즉각 피드백이 뜨는가

  • 브라우저 기본 검증은 novalidate(index.html:77)로 껐다. 네이티브 풍선이 먼저 뜨면 내 커스텀 문구가 가려지기 때문이다.
  • 오류는 입력칸에 aria-describedby로 연결된 role=alert 자리에 뜬다. 스크린리더도 같은 문구를 읽는다.
이 '즉각'은 처음부터 있던 게 아니다. 네이티브 검증을 끄기 전에는 커스텀 문구가 아예 못 떴다. 자체 점검으로 발견한 결함이고, git log에 수정 내역이 그대로 남아 있다.
검증은 막고·검사하고·알리고. 알리는 자리는 접근성 트리와 같은 자리다.
빈값 제출 → 세 문구 → 타이핑하자마자 오류 문구가 지워지는 것 → 정상 제출 후 초기화까지.

Q6. 왜 세 개의 파일인가

  • index.html은 구조, css/style.css는 표현, js/main.js는 동작. 관심사를 나눠서 한 파일을 고쳐도 나머지가 안 무너진다.
  • 연결의 증거는 두 줄이다. css link(index.html:10)와 <script … defer>(:24). defer는 HTML 해석을 막지 않고, 해석이 끝난 뒤 순서대로 실행하라는 뜻이다. async는 다운로드가 끝나면 중간에라도 실행돼서 DOM이 아직 없다. 원문이 defer를 요구한 이유다.
  • 같이 지켜진 규칙: var 금지(함수 스코프·호이스팅·중복 선언 때문에 기본 const, 재할당만 let), 인라인 onclick 금지, 인라인 스타일 금지.

index.html:10, 24 두 링크 · js/main.js:4 DOMContentLoaded

분리의 증거는 HTML의 두 링크와 JS의 준비 보장 하나. 이 세 줄이면 설명이 끝난다.
index.html을 열고 두 링크를 손으로 가리켜 보자. JS 파일에는 onclick이 하나도 없다.

Q8. CSS 변수를 왜 모았나

Q9. onclick 대신 addEventListener

  • 구조와 동작을 분리한다. HTML에 행동을 박아두면 세 파일로 나눈 의미가 무너진다.
  • onclick은 속성 하나라서 두 번째가 첫 번째를 덮어쓴다. addEventListener는 같은 요소에 여러 리스너를 붙일 수 있다.
  • 이 코드에 리스너는 열 곳이다. index.html을 검색하면 onclick은 없다.

js/main.js:36, 54, 64, 71, 143, 157, 164, 171, 234, 272

이벤트 위임(event.target.closest)은 9/19에 들어왔다. 원래는 필터 버튼도 생성마다 하나씩 붙였는데, 목록을 다시 그릴 때마다 리스너를 다시 붙여야 해서 리팩터링했다. 지금은 renderFilters가 버튼에 data-filter 값만 싣고(:227), 클릭은 부모 #repos-filters 리스너 하나가 받아서 눌린 버튼을 closest로 고른다(:234-239). 개선 전후가 Git 로그에 있다.
없는 걸 증명하는 건 있다고 설명하는 것보다 쉽다. onclick 0건은 검색 한 번이다.
Elements에서 onclick을 검색해서 0건을 눈으로 확인하자.

Q10. 다크모드 한 흐름을 처음부터 끝까지

  • 콘솔에 window.__B11_DEBUG = true를 치면 그 뒤부터 상태 변경이 로그로 찍힌다(:21). 평소에는 조용하다. 볼 때만 켠다.
한 흐름의 여덟 단계를 처음부터 끝까지 말할 수 있으면, 목록과 폼도 같은 모양이라는 걸 알게 된다.
디버그를 켜고 토글을 눌러보자. 로그의 {theme: 'dark'}를 가리키며 위 여덟 단계를 말하면 이 장은 끝이다.

Q11. async/await·try/catch의 분기 따라가기

  • try 안의 순서: 로딩 상태 세팅 → fetch(url, {signal}) → res.ok 검사 → json() → 렌더. 각 단계에서 실패하면 던지는 지점이 다르다.
  • 분기 네 개가 코드에 따로 존재한다. 403은 한도 초과 문구(:256), 404는 사용자 없음(:257), 그 외 HTTP는 상태 코드 문구(:258), 망 단절과 타임아웃은 catch(:262-265). 타임아웃은 8초에 controller.abort()를 걸고(:247-251), finally에서 타이머를 정리한다(:266-268).
  • "catch 하나로 다 처리"가 아니다. 실패의 종류마다 화면 문구가 달라야 해서 분기도 나뉘어 있다.

js/main.js:244-273 요청부터 정리까지 한 덩어리

실패의 종류가 다르면 문구도 다르다. 분기는 catch 하나가 아니라 코드 네 곳에 있다.
Network 탭 Offline에서 '다시 시도'까지, catch 경로를 실제로 타는 것을 보자.

Q12. 데이터가 카드가 되는 세 단계

  • map 안에서 두 가지가 더 일어난다. 구조분해(:207)로 값을 꺼내고 템플릿 리터럴(:209)로 조립한다. forEach는 목록 전체를 다시 쓰지 않고 insertAdjacentHTML('beforeend')로 하나씩 붙인다.
  • 심기 전에 이스케이프가 한 단계 더 있다. API에서 온 name이나 description은 외부 데이터라서, escapeHTML(:185-192)로 태그 문자를 전부 안전 문자로 바꾼 뒤 넣는다. 안 그러면 이름에 스크립트를 심은 저장소가 내 페이지에서 실행될 수 있다.
고르고, 바꾸고, 안전 문자로 바꾸고, 꽂는다.
언어 필터 칩을 누르면 목록이 즉시 갈아끼워지는 걸 볼 수 있다.

Q13. Flex와 Grid는 어디에, 왜

  • Flex는 한 축이다. 헤더 한 줄, 내비 한 줄, 필터 한 줄처럼 좌우 정렬만 필요하면 1차원으로 충분하다(css/style.css:172, :509-517, :318).
  • Grid는 두 축이다. 카드는 행과 열이 같이 굴러가야 해서 2차원이다. 기본은 1열(:332-336)이고 넓어지면 repeat(auto-fit, minmax(260px, 1fr))(:533)이 남는 폭을 쪼개 열을 늘리고, 1200px 이상에서는 repeat(4, 1fr)로 명시 고정한다(:571). 카드가 적어도 빈 트랙을 접어서 채운다. auto-fill이었다면 빈칸을 남겨 한쪽으로 쏠린다.
README가 내비에게 기대한 space-between은 9/19에 사실이 되었다. 768px부터 내비는 flex: 1 + space-between으로 링크 4개를 폭 전체에 균등 배치한다(:513-514). 푸터는 원래부터 space-between(:428)이었고, 모바일 행의 테마 버튼 우측 정리는 margin-left: auto(:189)가 맡는다.
한 줄 정렬은 Flex, 격자는 Grid. auto-fit이 격자를 스스로 채운다.
창을 넓히며 카드 열이 늘어나다 1200에서 4열로 고정되는 것을 보고, 내비(:513)와 푸터(:428)의 space-between 두 개를 코드에서 찾아보자.

Q14. STATE 객체가 왜 필요한가

  • 화면을 결정하는 값 네 개(theme, menuOpen, repos, reposFilter)를 한 객체에 모아뒀다. 바꾸는 통로는 setState 하나, 보는 함수들은 읽기만 한다. 상태가 어디에서 변하는지 묻는 질문에 한 곳으로 답한다.
  • 변수로 흩어두면 어떤가. 핸들러가 늘수록 "지금 이 화면을 결정하는 값이 뭔지"를 역추적하기 어렵다. 값 변경 지점이 한 곳이라 디버그 로그도 한 곳에 붙는다.

js/main.js:10-15 STATE · :19-22 setState와 로그

정직하게 말하면 예외가 두 개 있다. 폼의 유효성(valid, :147)은 지역 변수에 바로 쓰고, 스크롤(300/60px, :64-68)은 화면을 '결정'하는 값이 아니라 지나가는 신호라서 클래스를 바로 토글한다. STATE의 경계를 이렇게 긋고, 그 이유까지가 설계 판단이다.
단일 진실 원천은 전부 모은다가 아니라, 뭐 모으고 뭐 두지 않았나를 설명할 수 있어야 성립한다.
에디터에서 setState를 검색해서 호출부를 세어보자. 폼과 스크롤이 안 걸린다.

Q15. 모바일 퍼스트로 쓴 이유

  • 기본 스타일이 곧 좁은 화면이다(내비 숨김 css:193, 기술 목록 1열 :293, 저장소 격자 1열 :333). 넓어지는 분기 min-width 세 개로 키운다.
  • 여기서 계산이 하나 사라진다. 데스크톱을 기본으로 두면 좁아질 때마다 max-width로 하나씩 되돌려가야 한다. 기본이 좁으면 분기는 넓어지는 방향 한쪽뿐이다. style.css에 max-width 미디어쿼리는 없다.
  • Q1과 뿌리는 같고 물리는 결이 다르다. Q1은 동작을 묻고 이 장은 그 순서를 고른 이유를 묻는다.
기본을 좁게 두면 역계산이 없어진다. 저사양·터치가 먼저 보장된다.
창을 좁혔다 넓혔다 하며 양쪽 방향을 다 넘겨보자. 분기가 넓어질 때만 도는 게 보인다.
